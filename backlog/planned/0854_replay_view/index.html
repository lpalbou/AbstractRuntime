    0854 — Replay view: one reducer of a run tree's ledger, served as a view every client renders¶

    Status: planned, in progress (runtime slice released in abstractruntime 0.14.0, 2026-10-27, PR #8 merge 0efe68f; gateway routes and client migration remain) · Priority: P0 · Created: 2026-10-27 Package: abstractruntime (reducer, durable cursor, conformance fixtures, ADR) · Slices: abstractgateway (routes, cache), every client that renders runs (migration) Master item: framework root backlog 0993, abstractframework/docs/backlog/planned/0993_one_ledger_replay_many_views.md Release wave: framework root backlog 1055, abstractframework/docs/backlog/planned/1055_release_wave_2026_10_27_voice_library_replay_memory.md (abstractruntime 0.14.0 carries this item; abstractgateway 0.16.0 waits for it) Cross-package: AbstractGateway backlog 0082 (abstractgateway/docs/backlog/proposed/0082_ledger_replay_integrity_and_durable_cursor.md), 0075 (abstractgateway/docs/backlog/proposed/0075_event_driven_ledger_streaming.md), 0943 (abstractgateway/docs/backlog/planned/0943_replay_view_routes_cache_and_client_migration.md), 0939 (sessions index, out of scope here); AbstractAssistant backlog 0008 (abstractassistant/docs/backlog/planned/0008_v2_runtime_replayer_adr_compliance_hardening.md) ADR: ADR 0010 — One replay, many views

    Summary¶

    Every client that shows a run (status, the approval or question it waits on, tool rows, replies, activity) rebuilds that state today from raw ledger records, run snapshots and its own memory, each in its own way. This item puts the one reconstruction in AbstractRuntime: a pure, deterministic reducer abstractruntime.replay that folds a run tree's ledger records and durable snapshots into a versioned JSON view (replay_view_v1), incrementally with apply. AbstractGateway serves that view and its deltas; clients render it and act through the gateway's commands. Each client deletes its private reconstruction once it passes the conformance suite.

    This item also records the inventory of every reconstruction path that exists today (master item 0993, scope step 1), with file:line anchors and the points where each path can disagree with the reducer.

    Why¶

    Operator, 2026-09-30, after the delegated-approval bug: "there should be only one unified way to replay the ledger, on top of which we could have different views, but only one way to replay the ledger." Operator principles this item implements (quoted as given):

    • "logic should not be in the thin client" (2026-10-01; full text in 0993: "full execution must happen in gateway/runtime and clients just read what's happening + forward execution parameters and requests/interactions from the user; all of that should be handled by the replayable ledger").
    • "each client decides what to show and how to forward requests from users and entities".
    • "workflows are the framework's central native primitive (agents, automations, trigger responses are workflows)": the view names the workflow (bundle, version, flow, entrypoint) each run executes and keeps the run tree (delegation) explicit.
    • "special attention to performance (caching, indexing, leveraging the runtime/ledger, the file<->SQL coupling)".

    panel-chat (@abstractframework/panel-chat 0.4.1, abstractuic/panel-chat/src/workflow_runtime.ts); used by AbstractCode web and any host that embeds the chat¶

    • Cursor and dedup. Record identity is ${runId}:${cursor} where the cursor is the bundle's or the page's record index (:865-869); a record arriving with a different index (bundle tail vs page) is folded twice.
    • Status. Only from GET /runs/{id} (updateRunState, :1217-1235); the bundle's snapshot is ignored for lifecycle (:775-777). Ledger terminal records are not read.
    • Interaction. Any waiting record that is not a delegation becomes the interaction, the latest arrival winning (foldRecord, :929-934; interactionWith, :516-521); a snapshot wait is adopted unless the ledger's resume resolved that key (adoptDurableWait, :530-538, resolvedWaits, :288). The interaction is cleared only by a resume record with result.resumed === true (:937-944) or a terminal run state. Event waits are presented as a "Send event" interaction (present_interaction.tsx:111).
    • Tools. foldWorkflowTools (workflow_evidence.ts:193): a waiting record whose payload is a $slim pointer falls back to result.wait.details.tool_calls (:202-209); identity is runtime_call_id/call_uid, else idempotency_key|step_id|cursor plus the call index.
    • Messages. answer_user records (:887-893), abstract.message events (:896-907), the bundle's session turns and input prompt (:762-774); the final answer comes only from a terminal run snapshot's output (:1225-1233).
    • Client-held state. approvedWaits, grantedToolWaits (:279-282), the automatic approver (autoApproveCurrentWait, :588), the stop evidence (:972).
    • Divergence. (1) No "later step closes a wait" rule: a timer or event wait with no resume record stays snapshot.interaction until a terminal snapshot. (2) "Latest arrival wins" depends on which child stream delivers first; the reducer orders by (record time, seq, run id). (3) Event waits are person-facing here and not in the reducer's interaction (they are in open_waits). (4) The root's final message waits for the snapshot; the reducer takes the ledger's system:completion:* record first. (5) Index cursors: a migrated or windowed ledger can repeat or skip records. (6) A timed 2 s GET /runs poll per open conversation.
    • Evidence of the 0.1.20 fix. abstractuic/panel-chat/scripts/check_approval_sync.mjs with the redacted live fixture scripts/fixtures/run_approval_subrun.json (header :1-15); AbstractCode web/e2e/approval_sync.spec.ts. Both become conformance cases (see below).

    Decision¶

    Taken; recorded here, not re-opened.

    • The reducer lives in AbstractRuntime as abstractruntime.replay: pure, deterministic replay(records_by_run, runs_by_id) -> ReplayView; incremental apply(view, new_records), whose delta is view.last_delta; versioned JSON replay_view_v1 (ReplayView.to_json()); the client side of a delta in replay/delta.py. replay(all records) == apply record by record, by construction (replay is apply over every record).
    • AbstractGateway serves the projection (gateway 0943):
    • GET /api/gateway/runs/{run_id}/view: the view; ETag = the view's cursor.token; a matching If-None-Match answers 304.
    • GET /api/gateway/runs/{run_id}/view/stream (SSE): one view event, then delta events produced by the runtime's apply; the event id and Last-Event-ID are the cursor token; driven by the ledger append subscription of the runs in the tree, no timed re-parse.
    • A per-run view cache, advanced by apply on append (never rebuilt from scratch while it is warm), dropped when the run tree changes in a way apply cannot fold.
    • Authorization as GET /runs/{id}.
    • Clients act through the existing routes: POST /api/gateway/commands (the view's interaction.command is the resume to send, the client adds the answer under payload.payload) and /runs/start. The view adds no command route.
    • The durable cursor is the per-run ledger seq. JSONL persists it on append (under the advisory lock of 82c0c74), SQLite has it in the table, list_after exists on every store, import_records keeps it across a file to SQLite migration (the gateway's migrate.py moves to it). The view's cursor.token is <run id prefix>:<seq> per run of the tree, joined by ..

    Trade-offs against the three options of 0993:

    • (a) Server-side projection — chosen as the delivery: clients become thin, the Rust and Qt clients need no reducer port, the gateway can cache and index (one fold per run tree shared by every viewer instead of one fold per client), and storage encodings ($slim, windows, index cursors) stay server-side. Cost: the gateway holds a view per watched run tree, bounded by the cache.
    • (b) One shared client reducer package (TypeScript plus Python/Rust ports): rejected. Three implementations to keep equal is the problem this item removes.
    • (c) Both (server authoritative, client reducer for latency): rejected for now. The view stream's deltas are the live path; llm.delta live text keeps flowing on the ledger stream as today. Offline replay of an exported ledger is served by the same Python reducer (replay(records_by_run, runs_by_id)), not by a client port. Revisit only with a measured latency gap that the delta stream cannot close.

    The view model (replay_view_v1, as implemented in replay/view.py)¶

    Top level (ReplayView.to_json):

    • version: "replay_view_v1".
    • root_run_id.
    • workflow: what the root run executes, {id, bundle_id, bundle_version, flow_id, entrypoint} (workflow_ref: bundle_id@version:flow_id, or a non-bundled id as its own flow; entrypoint is the flow the root was started at).
    • session_id (from the root snapshot).
    • status (running | waiting | completed | failed | cancelled | unknown) and display_status (the latest abstract.status text, never a terminal word).
    • cursor: {token, records, runs}:
    • token is header-safe: <run name>:<seq> per run, joined by .. A run's name is the shortest run-id prefix (8 characters at least, letters, digits, _ and -) that no other run of the tree shares, and resolve_cursor_token maps it back. The token serves as an ETag and as an SSE id.
    • records is the number of folded records.
    • runs maps each run id to its last folded seq.
    • runs[]: the tree in path order (order is the path from the root; a child follows its parent, and siblings appear in the order they were started): run_id, parent_run_id, workflow_id, workflow (as above, without entrypoint), status, display_status, depth, order, waiting ({kind, wait_key, child_run_id} or null), holds_interaction, records, first_seq, last_seq.
    • interaction: the one person-facing wait, or null. Its fields:
    • kind (tool_approval | ask_user | event), run_id, wait_key, step_id, seq;
    • prompt, choices, allow_free_text;
    • details (without tool_calls), and tool_calls (resolved, never a $slim pointer);
    • activity_id;
    • answer_payload (the resume payload's shape, from automations.attention.ANSWER_PAYLOADS);
    • command = {type: "resume", run_id, payload: {wait_key}}.
    • open_waits[]: every open wait in the tree. Its fields: run_id, kind, wait_key, step_id, seq, until, child_run_id, person_facing. The kinds are tool_approval, ask_user, event (person-facing), and delegation, timer, job, pause, automation_wake, signal (not person-facing).
    • Each delta (not the view) also carries changes[], the typed changes for push dispatch (root 1058):
    • every change has {kind, id, run_id, seq};
    • status changes add status and previous;
    • interaction changes add change: opened|closed, interaction_kind and wait_key;
    • run, message, activity and artifact changes have no extra fields.
    • messages[]: verbatim text with provenance: id, role, kind (prompt | answer | question | final | event), text, run_id, step_ids, seqs, artifact_ids, source (run_input | answer_user | wait | resume | emit_event | ledger | run_output), order, and per kind final, choices, wait_key, level.
    • activities[]: one per node execution: id (<run>:<execution id>), run_id, execution_id, node_id, kind (llm | tool | subworkflow | timer | event_wait | ask_user | answer | step), effect_type, name, status (running | waiting | completed | failed | cancelled | denied), started_at, ended_at, seqs, step_ids, order; per kind tool_calls[] (id, name, arguments, status, output, error), provider, model, usage, child_run_id, wait ({kind, wait_key, until, ended_by: resume | later_step | terminal}), progress, denied_reason, error.
    • artifacts[]: every {"$artifact": id} reference: id, run_id, step_id, seq, path.
    • usage: {input_tokens, output_tokens, total_tokens, llm_calls} over the tree.
    • warnings[]: what the view could not fold (a windowed history, an unresolvable $slim pointer), as sentences.

    Rules (module docstring and code of replay/view.py):

    1. Run tree. Children come from delegation waits (subworkflow:<id>, sub_run_id / child_run_id in wait details), start_subworkflow results, and snapshot parent_run_id. A ledger link (seq > 0) outranks a snapshot link, so a run's place does not depend on read order.
    2. Wait end. A wait is over when its run records a resume for its key or any later step of the same run; abstract.status and abstract.progress events are not steps. A terminal record also closes it. activities[].wait.ended_by records which.
    3. Interaction. The newest open person-facing wait (tool_approval, ask_user, or an event wait carrying a prompt or choices; wait_kind agrees with automations/attention.py, pinned by a test) anywhere in the tree, ordered by (record time, seq, run id). A delegation, timer, job, pause, automation wake or prompt-less event (signal) never is one; none once the root is terminal. A snapshot's wait is adopted only when the run's ledger never mentioned its key (a windowed or empty ledger).
    4. Status. A terminal snapshot wins; then the ledger's terminal record (system:terminal_status:<status>, system:completion:*, a run-level failure); then an open wait; then running. A snapshot that still says "waiting" for a key the ledger resolved reads as running (the resume-before-save window).
    5. $slim. Resolved against the STARTED record of the step the pointer names (an approved tool call completes under a new step id pointing back at the waiting step), only for the payload fields the view reads (tool_calls, prompt, message, text, content, provider, model, workflow_id); an unresolvable pointer is dropped and named in warnings.
    6. Executions. replay/executions.py: same step; a resume joins the execution whose wait it answers; a repeated idempotency key joins the node's latest execution; an Agent's _temp.agent.<node>.structured call and system:completion:* join the latest execution; progress ticks join the step they report on and never start one.
    7. Messages. The root's input prompt from its snapshot; answer_user text; ask-user questions and their answers; abstract.message events; the final answer from the root's system:completion:* record, else from a completed snapshot's output, always as <root>:final. A final answer equal to an earlier answer names it in repeats, and clients show the text once.
    8. Idempotence and order. Records carry their seq; a record at or below a run's folded seq is ignored. Records of different runs may arrive in any order. apply_delta(old, diff_views(old, new)) == new; list items are never removed from a view, only changed.

    Open points the conformance suite must settle before 0.14.0 (found by this inventory):

    • Settled (2026-10-27): an event wait with a prompt or choices is person-facing. The reducer's wait_kind agrees with automations/attention.py (pause, automation_wake and signal are not person-facing), and tests/test_replay_conformance.py compares the two on every wait of every fixture. Still open: the gateway's attention stream keeps its own copy (events_stream.py:848-852) and should call the runtime's classifier.
    • Settled: the raw ledger stream's id: ("records consumed") equals the record's seq, because every store now numbers records densely from 1 (a pre-seq JSONL line is numbered by its position). The view stream uses cursor tokens.

    Scope¶

    In (abstractruntime)¶

    • The reducer abstractruntime.replay (view, executions, delta), exported from the package root, documented in docs/ (architecture page and API reference).
    • The durable cursor: seq on every record of every store, list_after on every store, import_records keeping seq, seq passed to append subscribers.
    • One wait classifier: replay.wait_kind used by automations/attention.py (or the reverse), so the runtime has one answer to "is this wait a person's".
    • The conformance fixtures: redacted real ledgers plus run snapshots with the expected replay_view_v1, shipped as package data so the gateway and clients can run them; cases below.
    • ADR 0010 (one replay, many views; the cursor is seq; clients render the view).

    In (abstractgateway, tracked by 0943)¶

    • GET /runs/{id}/view (ETag, 304), GET /runs/{id}/view/stream (SSE view then delta, Last-Event-ID), the per-run view cache invalidated on append, authorization as GET /runs/{id}.
    • migrate.py through import_records; 0082 and 0075 closed against this item (0075's text corrected: the tail is already event-driven).
    • A benchmark: view build and apply cost on the largest ledgers of the operator's gateway, cache hit rate, one fold per tree whatever the number of viewers.

    In (clients, each in its own repo, in this order)¶

    1. panel-chat (WorkflowSessionController renders the view; ingestHistory, foldRecord, adoptDurableWait, resolvedWaits, foldWorkflowTools and the 2 s lifecycle poll go), then AbstractCode web (activity_rows reads activities[]; delete wait_resolution.ts, history_bundle_seed.ts, subworkflow_follow.ts).
    2. AbstractAssistant desktop (GatewayRunController and GatewayWorker follow the view stream; assistant 0008's replay findings close with it), then its iPhone and watch apps.
    3. AbstractObserver and AbstractFlow run views (Flow's executionIdFor is replaced by activities[].execution_id).
    4. The AbstractCode terminal client (the fold in transcript.rs and the bundle merge in runner.rs).
    5. The gateway web console and terminal console (status, interaction, run tree only).

    Each client deletes its private reconstruction once it passes the conformance suite; a client keeps only what it decides to show and how it forwards a person's or an entity's request.

    Out¶

    • The conversation list and its counts (gateway 0939).
    • Live token text (llm.delta frames stay on the ledger stream).
    • Any change to the ledger's append-only semantics or record format beyond seq.
    • A client-side reducer (option c), until a measured need.

    Acceptance criteria¶

    • [x] abstractruntime.replay exported; replay(all) == apply record by record on every conformance fixture; apply_delta(old, diff_views(old, new)) == new.
    • [x] Every store returns records with their per-run seq; list_after(after=seq) returns exactly the records after it on JSONL, SQLite and in-memory; a JSONL ledger migrated to SQLite keeps every seq, so a cursor held before the migration resumes at the same record.
    • [ ] Conformance fixtures with expected views. Fourteen cases ship in abstractruntime.replay.conformance: a, a2, b-h, i-l. Still missing: a question in a child, a snapshot read between resume and save, a reconnect at a cursor (covered by the gateway tests, not by a fixture), and records of a child arriving before its parent's link (covered by the invariants' interleavings). The cases this item asks for are: the 2026-09-29 delegated approval (run_approval_subrun.json), a question in a child, a parallel tool batch, an approved batch (new step id, same idempotency key), a denied batch, a timer wait without a resume record (2026-10-04), an Agent node with its structured output (2026-10-11), a cancellation, a windowed history with an unresolvable $slim, a snapshot read between resume and save, a reconnect at a cursor, records of a child arriving before its parent's link.
    • [ ] One wait classifier in the runtime; the gateway attention stream uses it.
    • [x] ADR 0010 accepted; docs/ describes the view and the cursor (docs/replay.md, docs/api.md).
    • [ ] Gateway 0943 done: /view, /view/stream, cache, benchmark; migrate.py keeps seq (implemented on feat/replay-view, merged with the gateway's 0.16.0 line).
    • [ ] panel-chat and AbstractCode web render the view and pass the fixtures; their private folds are deleted (the other clients follow in their own releases; each is tracked in its repo).
